# 08 · 决策记录（ADR）

> 格式：编号 · 标题 · 状态 · 背景 · 决策 · 理由 · 后果 · 替代方案。
> 想推翻某条设计时，先读对应 ADR，确认当时的约束是否已经变化。

---

## ADR-001 后端使用 Python FastAPI

- **状态**：已采纳（v0.2）
- **背景**：需要一个本地 API 服务，同时要复用已有的 baostock 数据管道与申万接口解析代码。
- **决策**：后端用 Python 3.13 + FastAPI，前端独立用 React。
- **理由**：
  1. baostock 只有 Python 客户端（私有 socket 协议），Node 无法直接调用；
  2. 上一阶段的抓取/校验脚本是 Python，复用成本最低；
  3. FastAPI 自带 OpenAPI 文档，本地调试方便。
- **后果**：项目有 Python 与 Node 两套运行时；部署时需同时装 Python 与（构建期的）Node。
- **替代方案**：Node 全家桶 + Python 子进程跑同步 —— 进程间通信与错误处理更复杂，否决。

## ADR-002 阶段一用 SQLite，而不是纯 JSON 或直接上 MySQL

- **状态**：已采纳（v0.2）
- **背景**：用户要求「数据先放本地文件，后期换 MySQL」。
- **决策**：用 SQLite 单文件 `data/astock.db`，表结构按 MySQL 习惯设计。
- **理由**：
  1. 仍是「本地文件」，但具备事务、索引、幂等 upsert，避免手写 JSON 锁；
  2. SQL 语义与 MySQL 基本一致，迁移只改连接串 + upsert 方言；
  3. 零安装，不阻塞当前迭代。
- **后果**：SQLite 并发写较弱（已用短事务 + 单飞同步规避）。
- **替代方案**：纯 JSON（无索引、全量重写、易损坏）；直接 MySQL（需先装 Docker/MySQL，拖慢交付）。

## ADR-003 行情存「前复权价 + 重叠校验重建」

- **状态**：已采纳（v0.2，可升级）
- **背景**：分红送转会重算整段前复权历史；直接增量追加会产生「同月两个价格」。
- **决策**：`price_daily.close` 存抓取时点的前复权价；同步时比对同月份重叠收盘价，偏差 > 0.5% 就重抓该股全历史并整只替换。
- **理由**：
  1. 绝大多数交易日只追加几行，成本最低；
  2. 漂移一年仅数次、每次少数股票，重建可接受；
  3. 实现简单，无需维护复权因子表。
- **后果**：历史价格不是「可回溯到任意时点」的严格版本；`sync_log.rebuilt` 需要监控。
- **替代方案**：`close_raw + adj_factor` 双列，查询时实时生成前复权 —— 更严格但复杂，列为 v0.5 可选升级。

## ADR-004 同步用「单飞 + 异步 job + 轮询」

- **状态**：已采纳（v0.2）
- **背景**：baostock 抓 156 只约 35 秒，不能阻塞 HTTP 请求；页面刷新需要感知进度。
- **决策**：`POST /api/sync` 立即返回 `jobId`，后台线程执行；前端每 1.5 秒轮询 `GET /api/sync/{jobId}`；进程内 `threading.Lock` 保证单飞。
- **理由**：实现最简；无需引入 Celery/Redis；本地单用户足够。
- **后果**：任务状态在内存，重启丢失（`sync_log` 仍落库）；多进程部署会失效。
- **替代方案**：同步阻塞（页面卡 35 秒）；WebSocket 推送（过度设计）；任务队列（本地无必要）。

## ADR-005 生产形态单端口 3999 托管前端

- **状态**：已采纳（v0.2）
- **背景**：用户要求「端口开在 3999」「前后端分离」。
- **决策**：开发时前端 5173（Vite 代理 `/api`），生产时 `npm run build` 产物由后端静态托管，只暴露 3999。
- **理由**：本地使用只记一个地址；无 CORS；部署简单。
- **后果**：前端改动需重新 build（除非跑 dev server）；后端需处理 SPA 回退。
- **替代方案**：Nginx 反代（本地多余）；前后端双端口常驻（用户要记两个地址）。

## ADR-006 用 SQLAlchemy Core + 手写仓储，不用 ORM Session

- **状态**：已采纳（v0.2）
- **背景**：5 张表、查询简单，未来要换 MySQL。
- **决策**：`db.py` 定义 Table，`repo.py` 用 `select/insert/update` 表达式；upsert 按方言分支。
- **理由**：无 Session 生命周期问题；SQL 可控；换库只改一处；比裸 DB-API 更安全（参数化）。
- **后果**：没有关系导航（如 `stock.industry`），需要手写 join；无自动迁移。
- **替代方案**：SQLModel/Django ORM（重）；裸 sqlite3（换库要改所有 SQL）。

## ADR-007 前端不引路由库/状态库/UI 框架

- **状态**：已采纳（v0.2）
- **背景**：只有两个页面，状态简单（version / syncing / refreshKey）。
- **决策**：hash 路由手写解析；`useState` + `refreshKey`；原生 CSS。
- **理由**：依赖少、包小、可控；ECharts 已是最大的依赖。
- **后果**：页面多了会难维护；无路由守卫/懒加载。
- **替代方案**：react-router + zustand + Ant Design —— 当前规模属于过度设计。

## ADR-008 MySQL 容器优先，ZIP 兜底，不推荐 MSI

- **状态**：已采纳（v0.2 结论，P6 执行）
- **背景**：本机无 MySQL、无 Docker；Win10 19045。
- **决策**：优先 Docker（mysql:8.4，映射 3307）；虚拟化不可用时用 ZIP 免安装版；不推荐 MSI 实机安装。
- **理由**：容器可重置、可复现、与未来生产一致；ZIP 不污染系统；MSI 卸载残留且占 3306。
- **后果**：容器方案需要先启用 WSL2/虚拟化（可能重启），有一次性成本。
- **替代方案**：MSI（快但脏）；云数据库（本地项目不必要）。

## ADR-009 行情数据源只用 baostock

- **状态**：已采纳（v0.2）
- **背景**：腾讯、新浪、baostock 都提供前复权数据，但**口径不同**。
- **决策**：只使用 baostock（个股 `adjustflag=2`，指数 `adjustflag=3`）。
- **理由**：实测三源区间收益差异可达 1~13 个百分点（个别 187 个百分点），混用会产生不可解释的断裂；baostock 前复权以最新真实价为基准，语义清晰。
- **后果**：依赖单一数据源；baostock 故障时无自动切换（备选源需重新校验口径后才能启用）。
- **替代方案**：多源投票/取中位数（复杂且无必要）。

## ADR-010 同步任务状态放内存

- **状态**：已采纳（v0.2，已知债务）
- **背景**：任务状态只需前端轮询期间可见。
- **决策**：`_JOBS` 字典 + 最近 20 条，进程重启即丢。
- **理由**：避免为临时状态建表；`sync_log` 已持久化审计信息。
- **后果**：重启后前端轮询旧 `jobId` 会 404；多实例不可用。
- **替代方案**：`sync_job` 表（列为 P7 债务 #1）。

## ADR-011 端口与路径参数化

- **状态**：已采纳（v0.2）
- **背景**：换机、端口冲突、多人环境。
- **决策**：所有可变项走 `ASTOCK_*` 环境变量；`config.py` 集中读取。
- **理由**：避免硬编码；部署时无需改代码。
- **后果**：环境变量未设置时依赖默认值，文档需与默认值同步。
- **替代方案**：配置文件 `config.yaml`（多一层解析，收益不大）。

## ADR-012 暂不迁移 MySQL：继续 SQLite，上公网且数据量增长后再切

- **状态**：已采纳（2026-11-20，长期形态结论）
- **背景**：本项目是本地研究服务，当前 15,576 行（约 0.4 MB）、单用户、单进程；P6 一直把「阶段二换 MySQL」列为待办，但本机尚无 Docker、WSL 未就绪（见 ADR-008）。2026-11-20 复核后确认短期没有迁移动因。
- **决策**：继续使用 SQLite。迁移 MySQL 的触发条件为**两条同时成立**：
  1. **服务上公网**（或需要多人 / 多机同时访问）；
  2. **数据量显著增长**：`price_daily` 超过约 1,000 万行，或库文件超过约 2~5 GB，备份与查询开始吃力。

  届时按 ADR-008 执行：优先 Docker（mysql:8.4，映射 3307），Docker / 虚拟化不可用则 MySQL 8.4 ZIP 免安装。
  例外：若上公网后出现多实例或并发写的硬需求，可不等待数据量阈值，直接评估迁移。
- **理由**：
  1. 当前规模 SQLite 读性能足够，单文件、零运维、备份直观；
  2. 代码已是双方言（`repo.upsert_prices` 按 `engine.dialect.name` 分支），迁移成本固定且已知（装 pymysql + 改 URL + seed + 一次同步），晚迁不会更难；
  3. 提前迁移会多一个常驻服务与端口 / 凭据 / 备份负担，当前收益为零；
  4. 仅更换数据库不会让服务变成多实例：任务状态仍在进程内存（ADR-010），多实例的前提是任务先落库。
- **后果**：SQLite 单写者模型会一直是约束（已用短事务 + 单飞同步 + 单进程规避）；单文件损坏风险靠「停服务后复制」的备份流程应对（`05-运行与部署.md` §7）。上公网前需重新评估鉴权、HTTPS 与并发（v1.0 范围）。
- **替代方案**：立即迁 MySQL（0.5~1 天，见路线图 P6）；纯 JSON（ADR-002 已否决）。**复核点**：服务上公网、或数据量触阈值时，重读本条并更新 P6。
