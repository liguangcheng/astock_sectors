# 03 · 数据结构

## 1. 实体关系

```
industry (31)
  code PK ─────────────┐
  name                 │ 1
  stock_count          │
  sort_order           │ N
                       ▼
                    stock (155)
                      code PK
                      name
                      industry_code FK
                      weight / rank / mktcap / is_leader / updated_at

price_daily (5,616)                ← 只存价格，不建外键到 stock
  code PK(1)                        （基准 000300 也在这里，但不在 stock 表中）
  trade_date PK(2)
  close / volume / source

sync_state (4)     键值对：seeded_at / last_trade_date / last_sync_at / last_sync_status
sync_log (N)       每次同步一行：窗口、新增行数、重建只数、状态、耗时
```

> **为什么 `price_daily` 不建外键**：基准指数 `000300` 不是股票，放不进 `stock`；且历史行情即使股票被移出行业也应保留。用应用层保证一致性（`seed.py` 先写行业再写股票）。

## 2. 表逐字段说明

### 2.1 `industry` — 申万一级行业（31 行）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `code` | VARCHAR(16) | PK | 行业代码，6 位，如 `801080`（电子） |
| `name` | VARCHAR(32) | NOT NULL | 行业名称，如 `电子` |
| `stock_count` | INTEGER | NOT NULL | 该行业成分股数量（申万口径，如电子 497） |
| `sort_order` | INTEGER | NOT NULL | 展示排序，按报告中的行业顺序 |

### 2.2 `stock` — 龙头股（155 行）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `code` | VARCHAR(8) | PK | 股票代码，如 `688256` |
| `name` | VARCHAR(32) | NOT NULL | 简称（已去空格，`万  科Ａ` → `万科A`） |
| `industry_code` | VARCHAR(16) | NOT NULL, FK, INDEX | 所属申万一级行业 |
| `weight` | FLOAT | NOT NULL | 申万行业指数权重（%），排序依据 |
| `rank` | INTEGER | NOT NULL | 行业内排名，1 = 权重第一（龙头） |
| `mktcap` | FLOAT | NULL | 总市值（亿元），展示用 |
| `is_leader` | BOOLEAN | NOT NULL | 当前恒为 true；预留给「非龙头但保留」的场景 |
| `updated_at` | VARCHAR(32) | NULL | 最近一次维护时间 `YYYY-MM-DD HH:MM:SS` |

索引：`ix_stock_industry_code`（按行业查龙头）、主键 `code`。

### 2.3 `price_daily` — 行情（5,616 行 = 155 只 × 36 个月 + 沪深300 × 36 个月）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `code` | VARCHAR(8) | PK(1) | 股票代码；`000300` 表示沪深300 基准 |
| `trade_date` | VARCHAR(10) | PK(2) | 交易日 `YYYY-MM-DD` |
| `close` | FLOAT | NOT NULL | **前复权**收盘价（基准为指数点位） |
| `volume` | FLOAT | NULL | 成交量（手），种子数据为 NULL |
| `source` | VARCHAR(16) | NOT NULL | `seed` / `seed-index` / `baostock` |

主键 `(code, trade_date)` 同时是幂等键：`INSERT ... ON CONFLICT DO UPDATE` 可安全重跑。

**存储粒度**：当前以「月末行」为主（种子数据 36 个月/只），增量同步写入的是**逐日行**。
月度图表通过 `analytics.to_monthly()` 取每月最后一个交易日，两种粒度混存互不影响。

### 2.4 `sync_state` — 水位线（4 行）

| key | 示例值 | 用途 |
|---|---|---|
| `seeded_at` | `2026-11-15 21:xx:xx` | 种子导入时间 |
| `last_trade_date` | `2026-11-13` | 全库最新交易日 |
| `last_sync_at` | `2026-11-15 22:13:58` | 上次同步完成时间 |
| `last_sync_status` | `ok` / `failed` | 上次同步结果 |

> 读接口的「是否需要刷新」由 `MAX(trade_date)` 与「应到交易日」比较得出，不依赖 `last_sync_at`。

### 2.5 `sync_log` — 同步审计（每次一行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | 自增 |
| `started_at` / `finished_at` | VARCHAR(32) | 开始/结束时间 |
| `trigger` | VARCHAR(16) | `page` / `manual` / `seed` |
| `window_start` / `window_end` | VARCHAR(10) | 抓取窗口（日期） |
| `added_rows` | INTEGER | 本次写入/更新行数 |
| `rebuilt` | INTEGER | 因复权漂移而整只重建的股票数 |
| `status` | VARCHAR(16) | `running` / `ok` / `failed` |
| `message` | TEXT | 耗时或错误摘要（截断 400 字） |

## 3. 数据流

```
上一阶段 JSON
  data/selection.json   31 行业 + 前五（weight/mktcap）
  data/bs_month.json    155 只 + 000300 的 {月份: 收盘}
  data/sw_components.json  行业成分数
        │
        ▼  python -m app.seed
industry / stock / price_daily(source=seed)
        │
        ▼  页面刷新 / 手动同步（baostock）
price_daily(source=baostock)  ← 逐日追加；复权漂移时整只替换
        │
        ▼  GET /api/industries/{code}
analytics.to_monthly()  →  [{month, trade_date, close, ret, norm}]
analytics.metrics()     →  {cum_return, cagr, mdd, annual_vol, best, worst}
        │
        ▼
JSON → ECharts 折线/柱状
```

## 4. 复权策略（本库最重要的一条）

- 库里存的是**抓取时点的前复权价**，不是不复权价。
- 分红送转后，同一只股票的历史前复权价会整体下移；若直接追加，会出现「2024-06 有两个不同收盘价」。
- 同步时用**重叠月份**检测：取本次抓到的「最新月份最后一个收盘」与库内同月收盘比较，
  - 偏差 ≤ 0.5%：视为一致，只追加新日期；
  - 偏差 > 0.5%：视为复权因子变化，删除该股全部历史、重抓 `SEED_FROM` 起的数据并整只替换。
- 代价：漂移只发生在分红除权日，一年少数几次、每次影响少数股票，重建成本可接受。

> 若未来要求「历史价格可回溯到任意时点」，再升级为 `close_raw + adj_factor` 双列方案（见 08-决策记录 ADR-003）。

## 5. 容量与性能

| 项 | 当前 | 上限估算 |
|---|---|---|
| `price_daily` 行数 | 5,616（月末粒度） | 155 × 250 × 3 年 ≈ 116,000（全逐日） |
| 数据库文件 | 约 0.4 MB | < 30 MB（逐日 + MySQL 索引） |
| 单次查询 | 6 只 × 700 日 ≈ 4,200 行 | 60 只上限 ≈ 42,000 行，仍为毫秒级 |
| 同步耗时 | 156 只 / 约 35 秒（串行） | 与股票数线性相关 |

单表 10 万行以内，SQLite 完全够用；MySQL 迁移不是性能驱动，而是多端共享/运维规范驱动。

## 6. MySQL 兼容性

| 项 | SQLite | MySQL 8.4 | 处理方式 |
|---|---|---|---|
| 建表 | `metadata.create_all()` | 同 | 共用 `db.py` |
| 主键类型 | VARCHAR | VARCHAR(8) + utf8mb4 | 长度足够 |
| 浮点 | FLOAT（8 字节） | FLOAT（4 字节）→ 建议 DOUBLE | SQLAlchemy `Float` 映射为 FLOAT；如需精度可改 `Double` |
| 布尔 | INTEGER 0/1 | TINYINT(1) | 自动 |
| 自增 | `INTEGER PRIMARY KEY` | `INT AUTO_INCREMENT` | 自动 |
| Upsert | `ON CONFLICT` | `ON DUPLICATE KEY UPDATE` | `repo.upsert_prices` 按方言分支 |
| 字符集 | UTF-8 | 必须 `utf8mb4` | 连接串 `?charset=utf8mb4` + 库默认 |
| 大小写 | 表名大小写敏感 | Windows 下默认不敏感 | 全小写表名，避免差异 |

**切换后必须校验的 3 件事**：

1. 行数：`SELECT COUNT(*) FROM price_daily` 与 SQLite 一致（5,616）。
2. 抽样：`SELECT close FROM price_daily WHERE code='600519' AND trade_date='2026-11-13'` = `1435.26`。
3. 页面：`/api/industries/801120` 返回的 `metrics.cum_return` 与 SQLite 版本一致（`-8.49`）。

## 7. 建表与迁移脚本（规划）

当前无迁移工具；首次建表由 `init_db()` 完成。若新增字段，建议：

```sql
-- 示例：给 price_daily 增加复权因子列（未来可选）
ALTER TABLE price_daily ADD COLUMN adj_factor DOUBLE NULL;
CREATE INDEX ix_price_daily_date ON price_daily (trade_date);
```

并在 `db.py` 同步修改表定义，避免 `create_all` 与手工 DDL 漂移。

## 8. 数据质量检查口径

`GET /api/admin/quality` 当前检查：

| 检查 | 规则 | 输出 |
|---|---|---|
| 缺月 | 从基期到最后月份，逐月检查是否有数据 | `type: missing_month`，列出前 12 个缺失月 |
| 行业悬挂 | `stock.industry_code` 不在 `industry` 表中 | `type: orphan_industry` |

建议后续补充（见 07）：异常涨跌幅（单月 > 100%）、价格 ≤ 0、重复主键、基准缺失。
